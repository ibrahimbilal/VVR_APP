# Screensaver (deep)

Editor state is `useScreensaverStore` (`client/src/apps/frame-screensaver/stores/screensaver.ts`). Ranking state is untouched. Export uses the same queued multi-export pipeline as Shorts (snapshot per click, shared `exportQueueRunner.ts`). Defaults for new projects: **3840×2160 (4K)** output, **4 hours** duration, **Optimized CFR** at **60 fps**, quality **Balanced** (`DEFAULT_SCREENSAVER_OUTPUT`, `DEFAULT_DURATION_SECONDS`, `DEFAULT_SCREENSAVER_RENDER_MODE` in `shared/screensaver.ts`). Older saved projects without `renderingMode` stay on **Fast VFR** (not migrated).

Saved projects are IndexedDB records version 3 (`project:<id>`), with source and audio blobs and a render record per id. Version 1 loads with the old fit (contain, cover, blur) turned into a composition, profile `balanced`, encoder `cpu` when none was stored, and the saved frame rate left as it was. Version 2 keeps its composition. The original media blob is not rewritten. `clearRankingProject()` does not clear this store. The left column keeps the project name and drop zone fixed, with a bottom border under that block. The project list under them scrolls. A card is shown only after an image or video is uploaded. Each dropped file creates its own project (a blank editor receives the first file; the rest are new projects). There is no preview or upload status under the drop zone. Each card has an info icon colored by upload status (uploading, uploaded, failed); hovering it shows the file name, size, dimensions, and error. Click a card to open it. Downloaded cards stay at reduced opacity until export settings change. The row actions are rename, duplicate, create thumbnail and send to Image Motion (image projects only), delete, download, retry, and **Delete all** (projects that are still rendering are kept). **New project** in the header saves the current project and starts a blank one; it does not delete the others, and the blank one stays off the list until media is added. Opening a project restores its settings, subscribe overlay, and local files when those blobs are still in IndexedDB, and does not start a render. The list stays in last-edit order; selecting a project does not move it. A saved project that is missing from the in-memory list is added when it is opened.

The composition (`shared/screensaverComposition.ts`) is normalized to the output frame: crop in source space, placement, rotation, flips, opacity, adjustments, background, and frame id. Browser size and view zoom are not part of it. Preview and the static export PNG both use `composeCanvas.ts`. The fitted 16:9 preview stays centered horizontally and vertically in the stage.

Frames are uploaded PNG files or bundled defaults from `client/src/assets/frames/` (ids like `default:frame-1`). Picker thumbnails live in `client/src/assets/frames/thumbs/` (150px wide; regenerate with `npm run frames:thumbs -w client` after changing a source PNG). Preview and export still use the full PNG. `shared/screensaverFrames.ts` accepts `none`, a stored frame UUID, or a bundled default id; older preset names (classic, mat, rounded, arch) load as no frame. The Frames section shows bundled frames in a grid above the upload control, then uploaded PNGs (40 MB max) stored in `server/tmp/frames/`. The most recently uploaded frame in a batch is applied to the preview automatically. Clicking a thumbnail selects it. Clicking it again clears the frame. Draw order is background, the placed image, then the PNG stretched over the output. Transparent pixels show the picture. Static exports bake that PNG into the composition image. Video exports overlay the stored file in FFmpeg (bundled frames are sent as an upload when the server has no copy) and do not clip with a mask. Closing the tab or window purges frames, leftover `jobs/` work dirs, all server clips (except any clip locked by a running render), and finished files in `server/tmp/outputs/` via `POST /api/uploads/cleanup` (beacon). Downloading the MP4 does not remove uploads. IndexedDB keeps project settings across visits. Background audio and the source file are stored per project. A full page reload keeps those blobs and re-uploads the source if the server copy was purged. If a blob or the rendered file is already gone, the project metadata stays and the list says which asset is missing. SPA navigation within the app does not count as reload.

Adjustments (brightness, contrast, saturation, exposure, temperature, tint, highlights, shadows, sharpness, blur, grayscale, sepia) are baked into the static PNG, so that export matches the editor. Video exports send the same slider values through FFmpeg (`eq`, `exposure`, `curves`, `colorbalance`, `hue`, `colorchannelmixer`, `gblur`, `unsharp`). Canvas blur/sharpen is a box blur; FFmpeg uses `gblur` and `unsharp`, so a moving video can differ slightly from the preview. Static art does not, because the PNG is the source.

**Preview rendering:** The editor uses WebGL2 when available (`client/src/apps/frame-screensaver/lib/render/`), with Canvas 2D fallback. Output settings include **Preview rendering**: Auto, GPU (WebGL2), or CPU (Canvas 2D); default **CPU** when no preference is stored. Preference is stored in `localStorage` key `vvr-screensaver-renderer` (`auto` clears the key). Export still bakes adjustments on the CPU (`composeCanvas.ts`); 4K static export can run in `exportCompose.worker.ts`. Optional diagnostics: `?screensaver_diag=1` or `localStorage.vvr-screensaver-diagnostics=1`. Baseline protocol: `docs/screensaver-performance-baseline.md`.

**Rendering mode (Output):** **Optimized CFR** (default for new image projects) or **Fast VFR** (legacy). CFR shows frame rates 24/25/30/50/60 and quality High / Balanced / Compact. Fast VFR keeps Profiles (Static Art, Balanced, High, Animated) and fps 1/24/30/60. Optimized CFR is static-image only; video loops stay on Fast VFR. Segment duration, GOP, timescale, and cache keys stay internal.

Profiles (Fast VFR): Static Art (1 fps), Balanced (24 fps), High quality (CRF 16 or matching hardware CQ), Animated (30 fps). CPU quality for Balanced and Static Art stays CRF 20, preset veryfast. High uses CRF 16 and preset medium. Hardware maps are in `encoderArgs` (`server/src/encoders.ts`).

**Optimized CFR engine:** `server/src/screensaverCfr/` builds a frame-accurate timeline (static / dynamic regions), encodes reusable static segments (preferred **10 s**, remainder coin-change over 2/5/30/60 s), encodes subscribe animation via the real PNG overlay pipeline at the selected CFR rate, stream-copies concat (`-c:v copy`, timescale 60000), muxes audio without re-encoding video, then validates the PTS grid before marking the job complete. Quality presets: High CRF 18/medium, Balanced CRF 20/veryfast/GOP 2s, Compact CRF 24/veryfast/GOP 5s. H.264 level follows resolution/fps (5.2 for 4K60). Tests: `npm run test:screensaver-cfr`. Bench: `npm run bench:screensaver-cfr`. YouTube candidates: `npm run export:screensaver-cfr-youtube`. Report: [`docs/optimized-cfr-production-report.md`](docs/optimized-cfr-production-report.md). PoC retained: `npm run poc:optimized-cfr`.

Encoder choice is Auto, CPU, or one listed hardware encoder (Ranking and Screensaver). Screensaver defaults to **CPU** for new projects and **New project** reset; saved projects keep their stored encoder. Auto runs timed encodes per workload (`still_*`, `motion_30fps`, `compose_motion`, `ranking_motion`), caches in `server/tmp/encoder-cache.json`, and picks hardware only when more than 8% faster than libx264. Set `VVR_ENCODER_BENCH=0` to skip cold benchmarks (Auto uses CPU). An explicit encoder that fails init or the real encode stops the job; Auto retries on CPU with a warning.

Static images (Fast VFR without subscribe): the browser draws one full-resolution PNG and FFmpeg loops it at the chosen frame rate with no scale or color filters. Audio is a second input in that same process (loop, volume, fades). Saved version-1 projects keep their stored fps.

**Subscribe animation:** Optional static-image overlay in Settings (`shared/screensaverSubscribeAnimation.ts`, `EditorCanvas.vue` overlay). Styles: channel card (YouTube fetch for name/avatar/subscribers), subscribe-only, subscribe + alerts, like + subscribe + alerts; **size** as % of output width with per-style defaults; **edge distance** in export pixels (default 0) — horizontal inset from frame edges plus the same value as **bottom padding** inside the animation bitmap (not overlay Y). The overlay settings are saved with the screensaver project. **Main preview canvas** loops via `subscribeAnimationCanvasPreview.ts` (toggle “Show on preview canvas”). Preview and export share `renderSubscribeAnimationAt()`. **`SUBSCRIBE_ANIMATION_FPS`** (default **60**) × **`SUBSCRIBE_ANIMATION_DURATION_SEC`** (7) → **`subscribeAnimationFrameCount`** PNG uploads (`animationFrames`) plus `overlayX`/`overlayY` in project JSON. **Fast VFR** path: three segments in [`renderScreensaverHybrid.ts`](server/src/renderScreensaverHybrid.ts) with a shared `video_track_timescale` (60000), concat stream copy without `+genpts`, then audio mux. **Optimized CFR** path uses the CFR engine above. Screensaver export multer: **`SCREENSAVER_EXPORT_MAX_MULTIPART_FILES`** (animation cap + 4), **80 MB** per file. PNG byte budget scales with fps (`SUBSCRIBE_ANIMATION_UPLOAD_BUDGET_BYTES`). Tests: `npm run test:screensaver-subscribe`, `npm run test:screensaver-cfr`. Bench: `npm run bench:screensaver-subscribe`. Details: [`docs/screensaver-subscribe-animation.md`](docs/screensaver-subscribe-animation.md).

Video: stream copy (`-stream_loop -1 -c:v copy`) only when the source is H.264 yuv420p, already the output size, and the composition is a full-frame placement with no crop, rotation, flip, adjustment, or frame. Otherwise it re-encodes. A failed copy falls back to an encode and sets a warning. Smooth loops encode one crossfaded cycle, then copy that file for the full duration when the copy probe succeeds. The cycle file is in the job directory, which is deleted on finish, cancel, and error.

Job JSON adds optional `encoder`, `hardware`, `encodeFps`, `encodeSpeed`, `elapsedSec`, `etaSec`, and `stage`. Ranking leaves them null. ETA stays empty until progress is past 2% and at least 2 seconds have elapsed. Speed and fps come from FFmpeg `-progress`. Screensaver x264 thread count is `min(4, CPU count)`, overridable with `VVR_X264_THREADS`.

Size estimates use bytes/second measured on the 8-second baseline below (1080p still, 4K still, 1080p motion). Other sizes scale the 1080p rate by pixel count. The UI labels this as approximate. Audio adds 192 kbit/s when a track is present.

### Benchmark (8-second outputs, this Windows machine, 2026-10-22)

Baseline is the original graph: libx264, CRF 20, veryfast, `-threads 1`, 30 fps, scale/blur inside the encode. CPU and memory were often “not measured” because the sampler needs two samples 400 ms apart.

| Case | Resolution | fps | Wall | FFmpeg speed | Bytes | Valid |
| --- | --- | --- | --- | --- | --- | --- |
| Static image | 1920×1080 | 30 | 4.31s | 3.66x | 48156 | yes |
| Static image | 3840×2160 | 30 | 13.23s | 0.579x | 120820 | yes |
| Looping video | 1920×1080 | 30 | 3.57s | 2.32x | 313403 | yes |
| Looping video, blur | 1920×1080 | 30 | 8.75s | 0.869x | 313403 | yes |

Blur used about 368% CPU and 544 MB. The other baseline rows finished before a second sample.

Optimized CPU path (precomposed stills, x264 threads up to 4, no per-frame scale on stills). Decorative frames are drawn into the still PNG, so they do not add a second encode pass. There is no baseline row for frames.

| Case | Resolution | fps | Wall | FFmpeg speed | Bytes | Valid |
| --- | --- | --- | --- | --- | --- | --- |
| Static, precomposed | 1920×1080 | 1 | 0.27s | n/a (too short) | 23926 | yes |
| Static, precomposed | 1920×1080 | 30 | 1.83s | 4.72x | 54910 | yes |
| Static, precomposed | 3840×2160 | 1 | 1.00s | n/a | 48474 | yes |
| Looping video, re-encode | 1920×1080 | 30 | 2.24s | 3.5x | 388388 | yes |
| Looping video, blur | 1920×1080 | 30 | 4.65s | 1.97x | 388388 | yes |
| Looping video, stream copy | 1920×1080 | 30 | 0.27s | n/a | 188008 | yes |

On that pass, 1080p stills at the same 30 fps dropped from 4.31s to 1.83s. The 1 fps default dropped the 1080p still to 0.27s and the 4K still from 13.23s (30 fps) to 1.00s. Those 1 fps rows are a different frame rate, not the same encode with a faster preset. The blur loop dropped from 8.75s to 4.65s. Stream copy of an already-matching H.264 file was 0.27s versus 2.24s to re-encode a smaller source up to 1080p. A later pass on a busy machine was slower for the same CPU commands (1080p 30 fps still 6.64s) and is not used as the comparison.

Timed tests (3 seconds, 1080p, still, standard quality), not the 8-second exports:

- First test, before Media Foundation init was fixed: libx264 7.27x, Quick Sync 4.15x. NVENC could not load `nvcuda.dll`. AMF could not load `amfrt64.dll`. Auto selected CPU.
- After dropping `-hw_encoding true`: Media Foundation 6.15x, libx264 3.24x, Quick Sync 2.52x. Auto selected Windows Media Foundation. That second test ran while the machine was busier, so the 6.15x figure is not comparable to the 7.27x figure above. Both tests agreed Quick Sync was slower than libx264 here.

A static 1 fps file with the precomposed PNG matched the PNG at SSIM 0.995 (`npm run test:screensaver`).
